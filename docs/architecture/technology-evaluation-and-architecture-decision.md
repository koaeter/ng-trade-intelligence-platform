# Technology Evaluation & Initial Architecture Decision\n\n## 1. Purpose\n\nPrevious passes deliberately avoided choosing technologies before the domain, knowledge model and persistence boundaries were understood.\n\nThis pass evaluates candidate technology categories against those established requirements. The goal is to establish a coherent, supportable architecture that can evolve as the platform grows.\n\n## 2. Evaluation Criteria\n\nCandidates are evaluated against domain fit, data integrity, temporal data support, provenance, relationship/query capability, full-text retrieval, semantic/vector retrieval, analytical workload support, scalability, operational complexity, security, interoperability, portability, cost, ecosystem, and institutional/on-premise suitability.\n\n## 3. Candidate Architecture\n\nPrincipal candidates:\n- PostgreSQL for transactional/domain persistence\n- PostgreSQL + pgvector for an initial vector layer\n- Neo4j as a dedicated graph option\n- OpenSearch as a dedicated search/vector option\n- S3-compatible object storage for source artifacts\n- DuckDB/Parquet as an analytical processing option\n- Redis as an optional cache\n- A message/event mechanism only when asynchronous processing actually requires it.\n\nThese are architectural candidates, not mandatory final components.\n\n## 4. Relational Database — PostgreSQL\n\nPostgreSQL is the preferred baseline for the authoritative transactional/domain store. Its feature set includes transactions, constraints, JSON, indexing, partitioning, views/materialized views, replication, backup/recovery and security capabilities.\n\nStrong fit for users and authorization metadata, products, countries, HS classifications, regulatory instruments, provisions, requirements, agreements, preferences, provenance metadata, scenarios, workflow state and audit metadata.\n\n**Decision: Preferred baseline — PostgreSQL.**\n\n## 5. Vector Storage — pgvector\n\npgvector adds vector similarity search to PostgreSQL and supports exact search plus approximate HNSW and IVFFlat indexes. It can also be combined with PostgreSQL full-text search for hybrid retrieval.\n\nStrong initial fit for provision embeddings, document chunks, requirement embeddings, semantic similarity and early RAG/GraphRAG experiments.\n\nUsing pgvector initially avoids introducing a separate vector database merely to begin AI retrieval.\n\n**Decision: Preferred initial vector layer — pgvector within PostgreSQL.**\n\nRe-evaluate if retrieval scale or functionality later justifies a dedicated search platform.\n\n## 6. Dedicated Search — OpenSearch\n\nOpenSearch supports lexical, semantic and hybrid search, including vector search and RAG-oriented workflows. Hybrid retrieval is particularly relevant because this platform needs both exact legal matching and semantic retrieval.\n\nStrong fit for large document corpora, provision search, semantic search, hybrid retrieval, faceting, filtering and relevance tuning.\n\n**Decision: Do not require OpenSearch in the first implementation.**\n\nDesign the search abstraction so OpenSearch can be introduced without changing the domain model.\n\n## 7. Dedicated Graph Database — Neo4j\n\nNeo4j provides a property-graph model and Cypher query language. Its current platform also supports vector indexes.\n\nStrong fit for multi-hop regulatory relationships, agreement relationships, amendment/supersession traversal, product → requirement → provision → source paths and GraphRAG traversal.\n\nHowever, not every table needs to become a graph node. The graph should remain a semantic projection of governed domain data unless graph-native persistence is demonstrated to be necessary.\n\n**Decision: Keep Neo4j as the preferred dedicated-graph candidate, but defer mandatory adoption.**\n\n## 8. Object / Document Storage\n\nThe platform needs durable storage for official PDFs, gazettes, scanned documents, spreadsheets, HTML snapshots, OCR artifacts and extracted files.\n\nThe logical interface should be object-storage oriented, preferably S3-compatible, preserving deployment flexibility across on-premise infrastructure, private cloud and public cloud.\n\n**Decision: Use an S3-compatible abstraction for document/object storage.**\n\n## 9. Analytical Trade Data\n\nDuckDB is an analytical SQL database designed to run in-process and can work directly with CSV, JSON, Parquet and other analytical formats.\n\nInitial approach:\n- PostgreSQL for canonical/reference trade data where appropriate\n- Parquet for large analytical datasets\n- DuckDB for analytical processing and research workflows.\n\nDo not introduce a large distributed analytical platform prematurely.\n\n**Decision: Start lightweight with PostgreSQL + Parquet/DuckDB where justified.**\n\n## 10. Cache — Redis\n\nRedis is a suitable candidate for caching, rate limiting, ephemeral state and selected coordination workloads.\n\nPotential uses include short-lived query caching, rate limiting, job coordination and expensive computed-result caching.\n\n**Decision: Optional, not foundational.**\n\nAdd it when measured workload characteristics justify it.\n\n## 11. Event / Queue Infrastructure\n\nThe platform will eventually need asynchronous processing for document ingestion, OCR, embedding generation, graph projection, trade-data ingestion, regulatory monitoring and notifications.\n\nHowever, an event platform should not be introduced before asynchronous workload needs are demonstrated.\n\n**Decision: Start with a clear application/job abstraction. Introduce durable queues/events when processing volume, retry isolation or multiple consumers require them.**\n\n## 12. Initial Technology Architecture\n\nConceptually:\n\nWeb Application → API/Application Services → Domain Logic / AI-RAG / Ingestion\n\nPostgreSQL + pgvector form the initial persistence and semantic retrieval core.\n\nAdditional projections can later flow to:\n- Neo4j for graph workloads\n- OpenSearch for dedicated search\n- S3-compatible storage for source artifacts\n- Parquet/DuckDB for analytics.\n\nThese are evolutionary components, not mandatory day-one infrastructure.\n\n## 13. Initial Stack Recommendation\n\n### Required at first\n- PostgreSQL — primary transactional and domain store\n- pgvector — initial semantic retrieval/vector capability\n- S3-compatible object storage — source documents and binary artifacts\n- Parquet + DuckDB — analytical trade-data processing where appropriate.\n\n### Add when justified\n- Neo4j — when graph traversal complexity and scale justify it\n- OpenSearch — when document/search scale or retrieval-quality requirements exceed the initial search layer\n- Redis — when caching/rate limiting/ephemeral high-speed state becomes a measured requirement\n- Message broker/event infrastructure — when ingestion and AI processing require durable asynchronous workflows.\n\n## 14. Why This Architecture Is Deliberately Conservative\n\nA common AI-platform mistake is introducing PostgreSQL, Neo4j, a search engine, a vector database, Redis, Kafka and an LLM before workload evidence justifies the operational complexity.\n\nThat creates synchronization burden, duplicated data, more security surfaces, more monitoring, more deployment complexity and more failure modes.\n\nThe proposed architecture instead starts with PostgreSQL + pgvector + object storage + analytical files/processing and adds specialized infrastructure when actual workload evidence requires it.\n\n## 15. Technology Abstraction Boundaries\n\nThe application should not tightly couple business logic to storage vendors.\n\nExamples of domain-oriented interfaces:\n- ProductRepository\n- RequirementRepository\n- InstrumentRepository\n- EvidenceRepository\n- TradeDataRepository\n- DocumentStore\n- SearchService\n- GraphService\n- EmbeddingService\n- CacheService.\n\nThe domain layer should depend on contracts rather than Neo4j/OpenSearch-specific APIs.\n\nPrefer domain operations such as `findApplicableRequirements()`, `getEffectiveInstrument()`, `resolveHsClassification()`, `evaluateAgreementEligibility()`, `retrieveEvidenceForAssertion()`, `getTradeFlows()` and `compareMarkets()` rather than generic storage operations that hide domain meaning.\n\n## 16. AI Architecture Implication\n\nThe technology decision reinforces:\n\nUser → Query Understanding → Domain Query Planning → Deterministic Filters/Rules → Graph + Search + Structured Data → Evidence Assembly → LLM Synthesis → Cited Answer\n\nThe LLM should not directly query arbitrary databases and decide what is legally applicable.\n\n## 17. Security Architecture Implication\n\nStorage boundaries create security boundaries:\n\n- Application data: authentication, authorization, audit and least privilege\n- Regulatory artifacts: integrity, provenance, controlled modification and retention\n- Search/vector indexes: controlled access and protection against unauthorized source contamination\n- Analytical datasets: provenance, access controls, validation and versioning.\n\n## 18. Initial Architecture Decision\n\n**Adopt PostgreSQL as the initial authoritative transactional/domain platform, with pgvector for initial semantic retrieval, S3-compatible object storage for source artifacts, and Parquet/DuckDB for analytical trade-data workloads.**\n\nTreat Neo4j, OpenSearch, Redis and message infrastructure as optional evolutionary components whose adoption must be justified by workload, scale or capability requirements.\n\nRationale:\n- strong relational integrity\n- relatively small operational footprint\n- semantic retrieval capability\n- durable document storage\n- analytical flexibility\n- clear provenance\n- future graph/search expansion\n- reduced early synchronization complexity.\n\n## 19. Technology Decision Is Not Permanent\n\nRevisit the decision when measurable thresholds are reached.\n\n### Graph triggers\n- complex multi-hop queries become dominant\n- graph traversal latency becomes material\n- graph-specific query capability becomes central.\n\n### Search triggers\n- corpus size or query volume exceeds relational search suitability\n- hybrid relevance tuning becomes a core product requirement\n- advanced search features become necessary.\n\n### Analytics triggers\n- trade observations exceed practical relational/embedded-analysis patterns\n- concurrent analytical workloads materially affect application workloads\n- distributed processing becomes necessary.\n\n### Cache triggers\n- repeated expensive reads produce measurable latency/load\n- rate limiting or ephemeral coordination needs arise.\n\n### Event triggers\n- ingestion/AI workloads require durable asynchronous execution and retry isolation.\n\n## 20. Current Architecture Position\n\n```text\n                    ┌─────────────────────┐\n                    │    Web / Client     │\n                    └──────────┬──────────┘\n                               │\n                    ┌──────────▼──────────┐\n                    │ API / Application   │\n                    │ Services            │\n                    └──────────┬──────────┘\n                               │\n             ┌─────────────────┼──────────────────┐\n             │                 │                  │\n             ▼                 ▼                  ▼\n      Domain Logic        AI/RAG Layer       Ingestion\n             │                 │                  │\n             └──────────┬──────┘                  │\n                        ▼                         ▼\n                  ┌───────────┐             External Sources\n                  │PostgreSQL │\n                  │ + pgvector│\n                  └─────┬─────┘\n                        │\n          ┌─────────────┼──────────────┐\n          ▼             ▼              ▼\n      Graph*         Search*       Object Store\n      Neo4j         OpenSearch       S3 API\n          │\n          └─────────────┐\n                        ▼\n                  Analytics\n                Parquet/DuckDB\n\n      * introduced when justified\n```\n\n## 21.
